# STM32 看门狗与系统可靠性设计：从 IWDG/WWDG 到故障自愈架构

> 作者：蔡浩宇 | 嵌入式开发笔记

## 引言

实验室里跑得好好的设备，到了现场就每隔几天死一次；日志里查不到任何线索，串口最后一行输出停在三小时前；现场工程师唯一的解决办法是"拔电源再插上"——如果你做过量产电子产品，这个场景应该不陌生。

这些问题的共同点在于：**系统失效的方式，超出了开发者在实验室里能想到的范围**。电源纹波、静电、射频干扰、极端温度、内存踩踏、某个第三方库里的死循环、某个等待标志位时忘了加超时的 `while`……任何一条都可能让程序跑飞，而跑飞之后系统不会自己恢复。

看门狗（Watchdog）就是为这件事存在的。它的逻辑极其朴素：**程序必须周期性"报到"，超时不到就认为系统已经失控，强制复位。**

但真实工程里，看门狗的难点从来不是"怎么打开"——`HAL_IWDG_Start()` 一行就够了。真正的难点是这四件事：

1. **喂狗放在哪里才有效？** 放在定时器中断里喂，等于没装看门狗——主循环死了，中断照样喂狗。
2. **IWDG 和 WWDG 有什么区别，该用哪个？** 一个防"死等"，一个防"跑乱"，能力完全不同。
3. **RTOS 多任务环境下，主循环健康不代表任务健康。** 某个任务卡死，其他任务还在跑，看门狗根本不会触发。
4. **复位之后怎么知道为什么复位？** 没有复位原因诊断，所有现场问题都只能靠猜。

本文从 IWDG/WWDG 的硬件原理讲起，逐层递进到 RTOS 任务级健康监控框架、复位原因诊断、掉电保护，最后给出一份可以直接抄进项目的可靠性设计清单。上一篇（#21 STM32 ADC 采集与数字滤波）结尾预告过本篇，现在兑现。

## 1. 看门狗的本质：一个独立于 CPU 的倒计时器

先建立最核心的心智模型：**看门狗是一个独立于内核的硬件计数器，它有自己的时钟源，CPU 死了它照样在跑。**

```
                    ┌──────────────────────────────┐
   LSI 32kHz ──────►│  预分频器 (Prescaler)        │
   (独立时钟源)     │        ↓                     │
                    │  12位递减计数器 (Counter)    │
                    │        ↓                     │
                    │  计数到 0 ? ────► 复位信号 ──┼──► NRST (整个芯片复位)
                    │                              │
   写 0xAAAA ──────►│  重载计数器 (Reload) = 喂狗  │
   (键寄存器)       └──────────────────────────────┘
```

三个关键设计决定了看门狗为什么靠得住：

| 设计 | 作用 | 工程含义 |
|------|------|---------|
| **独立时钟源** | IWDG 用 LSI 内部低速 RC，不依赖 HSE/PLL | 外部晶振坏了、时钟配置错了，看门狗依然工作 |
| **键寄存器保护** | 必须依次写入特定键值才能改配置 | 程序跑飞后乱写内存，几乎不可能"碰巧"喂对狗 |
| **启动后不可关闭** | IWDG 一旦启动，除复位外无法停止 | 防止错误代码把看门狗自己关掉 |

STM32 提供了两个看门狗，能力差别很大：

| 特性 | IWDG 独立看门狗 | WWDG 窗口看门狗 |
|------|----------------|----------------|
| 时钟源 | LSI（约 32 kHz，独立） | PCLK1 分频（依赖 APB1） |
| 喂狗时机 | **任意时刻**（计数到 0 之前） | **必须在窗口内**（太早太晚都复位） |
| 超时范围 | 0.1 ms ~ 32.8 s | 约 0.1 ms ~ 100 ms（F4 @42MHz） |
| 中断 | 无 | 有提前唤醒中断（EWI），可"最后抢救" |
| 能防什么 | 死机、死循环、时钟失效 | 死循环 + **程序跑乱导致的喂狗过快** |
| 典型用途 | 兜底复位，必开 | 关键实时任务监控 |

一句话总结：**IWDG 是"最后一次兜底"，WWDG 是"运行时行为监控"。** 严肃的产品通常是 IWDG 做兜底 + 软件层做任务监控，两者组合。

## 2. IWDG 独立看门狗：系统的最后一道防线

### 2.1 超时时间计算

IWDG 的计数时钟为 `LSI / Prescaler`，计数器从 Reload 值递减到 0 触发复位：

```
T_timeout = (Reload + 1) × Prescaler / f_LSI
```

以 STM32F4 的 LSI = 32 kHz 为例（**注意：LSI 是 RC 振荡器，实际频率离散度很大，F4 标称范围约 30~60 kHz，设计时要留 2 倍以上余量**）：

| 预分频 | 分频系数 | 最小超时 (RL=0) | 最大超时 (RL=4095) |
|--------|---------|----------------|-------------------|
| `/4`   | 4       | 0.125 ms       | 512 ms            |
| `/8`   | 8       | 0.25 ms        | 1.024 s           |
| `/16`  | 16      | 0.5 ms         | 2.048 s           |
| `/32`  | 32      | 1.0 ms         | 4.096 s           |
| `/64`  | 64      | 2.0 ms         | 8.192 s           |
| `/128` | 128     | 4.0 ms         | 16.384 s          |
| `/256` | 256     | 8.0 ms         | **32.768 s**      |

工业设备常用的配置是 **预分频 /32 或 /64，超时 1~5 秒**——足够长（不会因为正常业务耗时而误触发），又足够短（死机后 5 秒内恢复）。

### 2.2 HAL 库配置

```c
#include "stm32f4xx_hal.h"

IWDG_HandleTypeDef hiwdg;

/**
 * @brief 初始化独立看门狗
 * @param timeout_ms 期望超时时间(ms)，按 LSI=32kHz 计算
 */
void IWDG_Init(uint32_t timeout_ms)
{
    /* 期望: timeout_ms = (RL+1) * presc / 32000 * 1000
     * 取 presc=64, 则 RL = timeout_ms * 32000 / (64 * 1000) - 1
     *                  = timeout_ms / 2 - 1
     */
    uint32_t reload = (timeout_ms * 32) / 64 - 1;    // LSI=32kHz
    if (reload > 0x0FFF) reload = 0x0FFF;            // 12位上限

    hiwdg.Instance       = IWDG;
    hiwdg.Init.Prescaler = IWDG_PRESCALER_64;
    hiwdg.Init.Reload    = reload;
    hiwdg.Init.Window    = IWDG_WINDOW_DISABLE;      // IWDG 无窗口功能

    if (HAL_IWDG_Init(&hiwdg) != HAL_OK) {
        Error_Handler();
    }

    /* 注意：HAL_IWDG_Init 内部会执行 HAL_IWDG_Start，看门狗自此开始运行
     * 且在本芯片上无法通过软件关闭（只能复位） */
}

/* 喂狗：向键寄存器写 0xAAAA，计数器重载 */
void IWDG_Feed(void)
{
    HAL_IWDG_Refresh(&hiwdg);
}
```

### 2.3 调试时的坑：调试器暂停导致误复位

默认情况下，**单步调试时程序停在断点上，看门狗仍在计时**，几秒后芯片直接复位，断点根本打不住。解决办法是让调试器暂停时同时冻结看门狗计数器（DBGMCU 的调试冻结位）：

```c
void IWDG_DebugFreeze_Enable(void)
{
    /* 内核暂停(Debug Halt)时, IWDG 计数器停止计数 */
    __HAL_DBGMCU_FREEZE_IWDG();     // 需要 __HAL_RCC_DBGMCU_CLK_ENABLE() 后调用
}
```

> **重要**：这个开关只在开发阶段使用。**量产固件绝对不能保留它**——否则一旦有人接上调试器，看门狗就形同虚设。稳妥做法是用宏区分：
> ```c
> #ifdef DEBUG
>     __HAL_DBGMCU_FREEZE_IWDG();
> #endif
> ```

### 2.4 独立看门狗的独有优势：STOP 低功耗模式下依然工作

IWDG 由 LSI 驱动，而 LSI 在 **STOP 和 STANDBY 模式下仍可保持运行**（通过选项字节配置）。这意味着：低功耗设备进入 STOP 休眠时，IWDG 依然在倒计时，如果唤醒逻辑失败导致"睡死"，看门狗会把它拉起来。

```c
/* 允许 IWDG 在 STOP 模式下继续计数（选项字节配置，非运行时 API） */
// FLASH_OPTR 的 IWDG_STOP 位 = 0 时, IWDG 在 STOP 模式继续运行
// 通过 STM32CubeProgrammer 的 Option Bytes 页面配置，或使用 HAL_FLASHEx_OBProgram
```

## 3. WWDG 窗口看门狗：不仅要"喂得勤"，还要"喂得巧"

### 3.1 为什么 IWDG 还不够？

考虑这个真实的 bug：

```c
void loop(void)
{
    while (1) {
        if (flag_ready) {
            process_data();     // 正常路径
        }
        // flag_ready 永远不来时的错误分支，被错误地"优化"成了跳过
        IWDG_Feed();            // 喂狗照常执行
    }
}
```

程序确实"活着"——没有死循环，没有卡死，IWDG 每毫秒被喂一次，看门狗永远不会触发。但**业务逻辑已经错了**：数据再也不被处理了。

IWDG 只能检测"程序停止执行"，无法检测"程序在错误地执行"。WWDG 的**窗口机制**就是来解决这个问题的：**喂狗不能太早**。

```
计数器值
0x7F ┬────────────────────────────────────  (起始值, T[6:0])
     │   ← 太早喂狗 → 复位
     │
 W   ├ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─   (窗口上限 W[6:0])
     │        ✅ 合法喂狗窗口
     │           (计数器 < W 且 > 0x3F)
     │
0x3F ├ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─   (窗口下限, 固定值)
     │        ↑ 到达 0x3F 时触发 EWI 中断
     │   ← 太晚不喂狗 → 复位
 0x00┴────────────────────────────────────  复位
             时间 →
```

如果程序跑飞后跳到了一段不断执行 `WWDG_Feed()` 的代码，它会在计数器值还很高（位于窗口之上）时喂狗，**立即触发复位**——这正是我们想要的行为。

### 3.2 超时与窗口计算

```
计数器时钟: f_cnt = PCLK1 / 4096 / (2^WDGTB)
超时时间:   T_wwdg = 4096 × 2^WDGTB × (T[5:0] + 1) / PCLK1
窗口时间:   T_win  = 4096 × 2^WDGTB × (T[5:0] - W[5:0]) / PCLK1
```

以 STM32F407（PCLK1 = 42 MHz）为例：

| WDGTB | 分频 | T=0x7F 最大超时 | T=0x7F、W=0x50 时窗口宽度 |
|-------|------|----------------|--------------------------|
| 0     | /1   | 12.48 ms       | 5.90 ms                  |
| 1     | /2   | 24.95 ms       | 11.81 ms                 |
| 2     | /4   | 49.90 ms       | 23.62 ms                 |
| 3     | /8   | **99.80 ms**   | 47.24 ms                 |

WWDG 的超时范围远小于 IWDG，因此它通常用于**监控毫秒级的严格时序**（例如电机控制主循环、通信协议状态机），而不是做整系统的兜底。

### 3.3 HAL 库配置与提前唤醒中断（EWI）

EWI 是 WWDG 最有价值的特性：**计数器到达 0x40 时先触发中断，再过最后一个计数周期才复位**。这意味着你有一段短暂的时间做"最后的抢救"——保存关键数据到 Flash / Backup RAM、拉高一个故障指示引脚、通过串口打印最后的现场信息。

```c
WWDG_HandleTypeDef hwwdg;

void WWDG_Init(void)
{
    /* PCLK1 = 42MHz, 目标: 超时约 50ms, 窗口约 24ms */
    hwwdg.Instance       = WWDG;
    hwwdg.Init.Prescaler = WWDG_PRESCALER_8;    // 2^3 = 8
    hwwdg.Init.Window    = 0x50;                // 窗口上限
    hwwdg.Init.Counter   = 0x7F;                // 起始计数值(最大)
    hwwdg.Init.EWIMode   = WWDG_EWI_ENABLE;     // 开启提前唤醒中断

    if (HAL_WWDG_Init(&hwwdg) != HAL_OK) {
        Error_Handler();
    }
}

/* WWDG 中断服务函数 */
void WWDG_IRQHandler(void)
{
    HAL_WWDG_IRQHandler(&hwwdg);
}

/* EWI 回调：计数器到达 0x40, 距复位仅剩 ~0.06ms (PCLK1=42MHz, WDGTB=3) */
void HAL_WWDG_EarlyWakeupCallback(WWDG_HandleTypeDef *hwwdg)
{
    /* ⚠️ 这里能做的事情极其有限, 只能做最关键的几步 */
    fault_log_save_to_backup();      // 保存故障现场到备份寄存器
    HAL_GPIO_WritePin(LED_ERR_GPIO_Port, LED_ERR_Pin, GPIO_PIN_SET);

    /* 注意：这里不能喂狗！喂狗会掩盖故障, 让系统永远无法复位恢复。
     * 唯一例外是"有意识地延迟复位以完成关键保存", 但必须确保最终会复位 */
}
```

> **一个常见误用**：在 EWI 回调里喂狗。这会让 WWDG 彻底失效——每次快到点了就续命，系统永远在"半死不活"的状态循环。EWI 的正确用途是**记录现场**，不是**逃避复位**。

## 4. 多任务环境的看门狗：任务级健康监控

这是从"能跑"到"能量产"的分水岭。

### 4.1 问题的本质

考虑一个 FreeRTOS 系统里有 5 个任务：

| 任务 | 周期 | 说明 |
|------|------|------|
| `task_sensor` | 100 ms | 传感器采集 |
| `task_comm` | 20 ms | 串口协议处理 |
| `task_display` | 500 ms | OLED 刷新 |
| `task_ctrl` | 50 ms | 控制算法 |
| `task_idle_hook` | — | 喂狗 |

如果 `task_sensor` 卡死在某个 `xSemaphoreTake(portMAX_DELAY)` 上，**其他任务照常运行，看门狗照常被喂，系统"看起来很健康"**——但传感器数据已经停止更新，控制算法正在用过期的输入做决策。这比整机死机更危险。

### 4.2 解决方案：任务心跳位图 + 监督任务喂狗

核心思想：**每个任务周期性上报"我还活着"，只有一个专门的监督任务负责喂狗，且它必须确认所有被监控任务都按时上报过。**

```
 task_sensor ──┐
 task_comm   ──┤
 task_ctrl   ──┼──► [ 心跳位图 bits ]  ◄──── 监督任务 task_wdog
 task_display──┘         (EventGroup)            │
                                                 │ 所有位都置起?
                             喂狗超时? ──────────┤
                                                 ↓
                                           HAL_IWDG_Refresh()
                                           并清空位图, 开始下一轮
```

实现（基于 FreeRTOS 事件组）：

```c
/* ---------------- watchdog_monitor.h ---------------- */
#ifndef WATCHDOG_MONITOR_H
#define WATCHDOG_MONITOR_H

#include "FreeRTOS.h"
#include "event_groups.h"

/* 每个被监控任务占用一个 bit */
typedef enum {
    WDOG_BIT_SENSOR  = (1u << 0),
    WDOG_BIT_COMM    = (1u << 1),
    WDOG_BIT_CTRL    = (1u << 2),
    WDOG_BIT_DISPLAY = (1u << 3),
    WDOG_TASK_MASK   = (WDOG_BIT_SENSOR | WDOG_BIT_COMM |
                        WDOG_BIT_CTRL   | WDOG_BIT_DISPLAY)
} wdog_bit_t;

void     wdog_monitor_init(void);
void     wdog_report_alive(wdog_bit_t bit);   /* 任务内调用: 上报心跳 */
uint32_t wdog_get_missing_mask(void);         /* 获取超时任务位图(诊断用) */

#endif
```

```c
/* ---------------- watchdog_monitor.c ---------------- */
#include "watchdog_monitor.h"
#include "stm32f4xx_hal.h"

#define WDOG_CHECK_PERIOD_MS   100     /* 监督任务检查周期 */
#define WDOG_GRACE_TICKS       3       /* 容忍连续 3 个周期不上报 */

static EventGroupHandle_t  s_alive_bits;
static volatile uint32_t   s_missing_mask = 0;
static volatile uint32_t   s_reset_count  = 0;
static uint32_t            s_streak[4]    = {0};   /* 各任务连续未上报次数 */

void wdog_monitor_init(void)
{
    s_alive_bits = xEventGroupCreate();
    configASSERT(s_alive_bits != NULL);
}

/* 被监控任务在其循环内调用, 表明自己完成了一轮工作 */
void wdog_report_alive(wdog_bit_t bit)
{
    if (s_alive_bits) {
        xEventGroupSetBits(s_alive_bits, bit);
    }
}

uint32_t wdog_get_missing_mask(void)
{
    return s_missing_mask;
}

/* 监督任务: 唯一有权喂狗的地方 */
static void task_wdog(void *arg)
{
    EventBits_t got;
    const uint32_t grace = WDOG_GRACE_TICKS;

    for (;;) {
        /* 等待任意任务上报心跳, 最多等一个周期 */
        got = xEventGroupWaitBits(s_alive_bits,
                                  WDOG_TASK_MASK,
                                  pdFALSE,     /* 不清位, 手动清 */
                                  pdFALSE,     /* 任意位置起即返回 */
                                  pdMS_TO_TICKS(WDOG_CHECK_PERIOD_MS));

        /* 逐个任务累加"未上报"计数 */
        const uint32_t bits[4] = { WDOG_BIT_SENSOR, WDOG_BIT_COMM,
                                   WDOG_BIT_CTRL,   WDOG_BIT_DISPLAY };
        uint32_t missing = 0;
        for (int i = 0; i < 4; ++i) {
            if (got & bits[i]) {
                s_streak[i] = 0;                 /* 收到心跳, 计数清零 */
            } else if (++s_streak[i] >= grace) {
                missing |= bits[i];              /* 连续多轮未上报 */
            }
        }

        /* 清除本轮已收到的心跳位, 开始下一轮统计 */
        xEventGroupClearBits(s_alive_bits, got);

        if (missing == 0) {
            /* 所有任务健康 → 喂狗 */
            HAL_IWDG_Refresh(&hiwdg);
        } else {
            /* 有任务失联 → 停止喂狗, 等待看门狗复位
             * 同时把故障信息写入备份寄存器, 复位后可读取 */
            s_missing_mask = missing;
            s_reset_count++;
            HAL_RTCEx_BKUPWrite(&hrtc, RTC_BKP_DR1, missing);
            HAL_RTCEx_BKUPWrite(&hrtc, RTC_BKP_DR2, s_reset_count);
            /* 不喂狗! 等待 IWDG 超时复位 */
        }
    }
}
```

被监控任务里的用法：

```c
void task_sensor(void *arg)
{
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        vTaskDelayUntil(&last, pdMS_TO_TICKS(100));

        sensor_read_all();
        sensor_filter();

        /* 只有在"完整完成了本轮工作"之后才上报心跳 */
        wdog_report_alive(WDOG_BIT_SENSOR);
    }
}
```

### 4.3 关键设计细节

| 细节 | 说明 |
|------|------|
| **心跳上报位置** | 必须放在**工作完成之后**，而不是循环开头。放在开头，任务卡死在中间也会被判为"健康" |
| **容忍次数 grace** | 不能为 1。任务可能因被高优先级任务抢占、偶发长耗时操作而漏报一次，直接复位会导致误触发 |
| **超时周期配比** | 检查周期 × grace 应显著小于 IWDG 超时时间。例如检查 100 ms × 3 = 300 ms，IWDG 设 2 s，留足余量 |
| **监督任务优先级** | 应设为**中高优先级**，确保它能及时运行；但不能是最高，否则它会饿死被监控任务 |
| **喂狗唯一性** | 全工程只有 `task_wdog` 一处调用 `HAL_IWDG_Refresh()`。用 `grep` 检查，出现第二次就要警惕 |

## 5. 复位原因诊断：让现场问题不再靠猜

复位之后，第一件事应该是**搞清楚为什么复位**。STM32 的 `RCC_CSR` 寄存器保存了复位源标志，这些标志在手动清除前一直保持（部分跨复位保持）。

| 标志位 | 含义 | 典型原因 |
|--------|------|---------|
| `RCC_FLAG_PINRST` | NRST 引脚复位 | 人为按复位键、外部复位芯片 |
| `RCC_FLAG_PORRST` | 上电/掉电复位 | 正常上电、电源跌落 |
| `RCC_FLAG_SFTRST` | 软件复位 | 调用了 `NVIC_SystemReset()` |
| `RCC_FLAG_IWDGRST` | **独立看门狗复位** | 程序死机/死循环 |
| `RCC_FLAG_WWDGRST` | **窗口看门狗复位** | 喂狗时机不对/程序跑乱 |
| `RCC_FLAG_LPWRRST` | 低功耗复位 | 从待机模式唤醒异常 |

```c
/**
 * @brief 打印并清除复位原因, 应在 main() 最开头调用
 */
void print_reset_cause(void)
{
    const char *cause = "UNKNOWN";

    if (__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST)) {
        cause = "IWDG (独立看门狗超时)";
    } else if (__HAL_RCC_GET_FLAG(RCC_FLAG_WWDGRST)) {
        cause = "WWDG (窗口看门狗喂狗异常)";
    } else if (__HAL_RCC_GET_FLAG(RCC_FLAG_SFTRST)) {
        cause = "SOFTWARE (软件复位)";
    } else if (__HAL_RCC_GET_FLAG(RCC_FLAG_PORRST)) {
        cause = "POR/PDR (上电/掉电复位)";
    } else if (__HAL_RCC_GET_FLAG(RCC_FLAG_PINRST)) {
        cause = "PIN (NRST 引脚复位)";
    } else if (__HAL_RCC_GET_FLAG(RCC_FLAG_LPWRRST)) {
        cause = "LOW-POWER (低功耗复位)";
    }

    printf("[BOOT] Reset cause: %s\r\n", cause);

    /* 如果是看门狗复位, 读出复位前保存的故障任务位图 */
    if (__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST)) {
        uint32_t missing = HAL_RTCEx_BKUPRead(&hrtc, RTC_BKP_DR1);
        uint32_t count   = HAL_RTCEx_BKUPRead(&hrtc, RTC_BKP_DR2);
        printf("[BOOT] Watchdog reset #%lu, missing task mask = 0x%02lX\r\n",
               count, missing);
        if (missing & WDOG_BIT_SENSOR)  printf("[BOOT]   -> task_sensor 失联\r\n");
        if (missing & WDOG_BIT_COMM)    printf("[BOOT]   -> task_comm   失联\r\n");
        if (missing & WDOG_BIT_CTRL)    printf("[BOOT]   -> task_ctrl   失联\r\n");
        if (missing & WDOG_BIT_DISPLAY) printf("[BOOT]   -> task_display失联\r\n");
    }

    /* 清除所有复位标志, 保证下次读到的是本次复位原因 */
    __HAL_RCC_CLEAR_RESET_FLAGS();
}
```

> **为什么用备份寄存器（RTC_BKP_DRx）而不是普通变量？** 因为备份域由 VBAT 供电，**普通复位不会清除它**。这让你能在复位后读到复位前写入的信息。如果设备有纽扣电池，断电也能保持。

有了这套机制，现场问题从"设备每隔几天死一次，原因不明"变成"日志显示 task_comm 连续 300 ms 未上报心跳，复位前最后一次上报在第 4721 轮"——定位效率天差地别。

## 6. 掉电、欠压与故障自愈

看门狗只解决"程序跑飞"，可靠性还需要覆盖另外几类失效。

### 6.1 PVD 可编程电压监测器

电源跌落时，MCU 可能在低于正常工作电压的状态下乱执行——这时看门狗未必来得及救。PVD 能在电压降到阈值时提前触发中断，让你有时间**在失控前保存数据**。

```c
void PVD_Init(void)
{
    PWR_PVDTypeDef sConfigPVD;
    sConfigPVD.PVDLevel = PWR_PVDLEVEL_7;   /* F4: 约 2.9V, 需根据实际供电选择 */
    sConfigPVD.Mode     = PWR_PVD_MODE_IT_RISING_FALLING;

    HAL_PWR_ConfigPVD(&sConfigPVD);
    HAL_PWR_EnablePVD();

    /* 使能 PVD 中断 (EXTI line 16) */
    HAL_NVIC_SetPriority(PVD_IRQn, 0, 0);
    HAL_NVIC_EnableIRQ(PVD_IRQn);
}

/* 电压跌落中断: 尽可能少做事, 只保存最关键的数据 */
void PVD_IRQHandler(void)
{
    HAL_PWR_PVD_IRQHandler();
}

void HAL_PWR_PVDCallback(void)
{
    if (__HAL_PWR_GET_FLAG(PWR_FLAG_PVDO)) {
        /* 电压已低于阈值 —— 立刻保存关键状态 */
        critical_data_save_to_flash();
    }
}
```

### 6.2 故障自愈策略：分级恢复

不是所有故障都需要整机复位。成熟产品的做法是分级降级：

| 级别 | 故障表现 | 恢复动作 | 数据损失 |
|------|---------|---------|---------|
| L1 | 单次通信超时/校验错误 | 重传，不复位 | 无 |
| L2 | 某外设连续 N 次失败 | **仅复位该外设**（`__HAL_RCC_xxx_FORCE_RESET()`） | 无 |
| L3 | 单个任务连续失联 | 删除并重建该任务 | 任务状态丢失 |
| L4 | 多任务失联 / 主循环卡死 | **看门狗整机复位** | RAM 数据丢失 |
| L5 | 关键数据区校验失败 | 恢复出厂参数 + 整机复位 | 配置丢失 |

```c
/* L2 示例：仅复位某个卡死的外设, 不影响系统其余部分 */
void peripheral_recover(PeriphId_t id)
{
    switch (id) {
    case PERIPH_I2C1:
        /* I2C 总线挂死(BUSY 位卡住)是经典问题, 用时钟脉冲+复位解决 */
        __HAL_RCC_I2C1_FORCE_RESET();
        HAL_Delay(2);
        __HAL_RCC_I2C1_RELEASE_RESET();
        MX_I2C1_Init();                 /* 重新初始化 */
        break;

    case PERIPH_UART2:
        HAL_UART_DeInit(&huart2);
        MX_USART2_UART_Init();
        HAL_UARTEx_ReceiveToIdle_DMA(&huart2, rx_buf, RX_LEN);
        break;

    default:
        break;
    }
}
```

> **I2C 总线挂死补充说明**：从机拉住 SDA 不放时，单纯复位 I2C 外设往往无效。标准做法是把 SCL/SDA 临时切成 GPIO 开漏输出，手动输出 **9 个时钟脉冲**，让从机释放总线，再切回 I2C 复用功能。

### 6.3 断言与错误处理

```c
/* 断言失败: 记录现场后主动复位, 而不是继续执行错误逻辑 */
void assert_failed(uint8_t *file, uint32_t line)
{
    __disable_irq();

    /* 保存故障文件与行号到备份寄存器(压缩存储) */
    HAL_RTCEx_BKUPWrite(&hrtc, RTC_BKP_DR3, line);

    printf("[FATAL] assert failed: %s @ %lu\r\n", file, line);

    /* 等待串口输出完成 */
    HAL_Delay(50);

    /* 主动软件复位, 保证系统恢复 */
    NVIC_SystemReset();
}
```

## 7. 看门狗的五个反模式

这些错误的共同点是：**代码看起来在喂狗，实际上看门狗根本没有起到保护作用。**

### 反模式 1：在定时器中断里喂狗

```c
/* ❌ 错误：主循环死了, 中断照样喂狗, 看门狗永远不触发 */
void SysTick_Handler(void)
{
    HAL_IWDG_Refresh(&hiwdg);
}
```

这是最常见也最致命的错误。定时器中断是硬件驱动的，与主程序逻辑完全解耦——主循环早就跑飞了，中断还在规规矩矩地喂狗。**正确做法：在主循环或专门的监督任务里喂。**

### 反模式 2：在阻塞等待里喂狗

```c
/* ❌ 错误：等到死也在喂狗, 永远等不到超时 */
while (!transfer_complete) {
    HAL_IWDG_Refresh(&hiwdg);   /* 这里喂狗 = 取消超时保护 */
}
```

所有等待循环都**必须有超时退出**：

```c
/* ✅ 正确：带超时的等待 */
uint32_t t0 = HAL_GetTick();
while (!transfer_complete) {
    if (HAL_GetTick() - t0 > 1000) {
        return ERR_TIMEOUT;      /* 超时返回错误, 由上层决定恢复策略 */
    }
    /* 等待期间不喂狗, 让看门狗能真正兜底 */
}
```

### 反模式 3：喂狗周期紧贴超时上限

LSI 频率离散度可达 ±50%。如果你按标称 32 kHz 算出 2.0 s 超时，而实际 LSI 是 24 kHz，真实超时只有 2.67 s；反之若 LSI 偏快，可能变成 1.6 s，而你的喂狗周期是 1.5 s——**正常运行时就会误复位**。

**工程准则：喂狗周期 ≤ 超时时间的 1/3。**

### 反模式 4：初始化阶段就开启看门狗

上电后系统可能需要几百毫秒做自检、外设初始化、从 EEPROM 读取配置。如果看门狗在 `main()` 第一行就启动且超时只有 1 s，某些慢速上电场景会**反复复位**。

```c
/* ✅ 正确：初始化完成后再启动, 或给初始化阶段设置较长的初始超时 */
int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();
    MX_USART2_UART_Init();
    /* ... 其他外设初始化 ... */

    print_reset_cause();      /* 先诊断复位原因 */
    IWDG_Init(4000);          /* 初始化完成后再开看门狗 */
    wdog_monitor_init();

    osKernelStart();
}
```

### 反模式 5：量产后保留调试冻结位

如 2.3 节所述，`__HAL_DBGMCU_FREEZE_IWDG()` 必须在发布版本中禁用。稳妥做法是在编译脚本里把 `DEBUG` 宏与发布构建严格区分，并在发布前用 `grep` 检查。

## 8. 可靠性设计清单

可以直接作为项目评审的 checklist：

**看门狗配置**
- [ ] IWDG 已启用，超时时间为最坏情况下喂狗周期的 3 倍以上
- [ ] 喂狗点唯一（全工程仅一处调用 `HAL_IWDG_Refresh`）
- [ ] 喂狗不在中断、不在阻塞等待循环内
- [ ] 初始化完成后才启动看门狗
- [ ] 发布固件已禁用调试冻结位

**任务监控**
- [ ] 每个关键任务周期性上报心跳，且上报位置在工作完成之后
- [ ] 心跳容忍次数 ≥ 2，避免偶发抢占导致误判
- [ ] 监督任务优先级合理，不会被饿死也不会饿死别人

**故障诊断**
- [ ] `main()` 开头读取并记录复位原因
- [ ] 看门狗复位前把故障信息写入备份寄存器或 Flash
- [ ] 关键状态（运行轮次、错误计数、最后心跳）可追溯

**失效防护**
- [ ] 所有阻塞等待都有超时退出
- [ ] `assert_failed` / `HardFault_Handler` 有明确的现场记录与恢复动作
- [ ] PVD 已配置，掉电前能保存关键数据
- [ ] I2C/SPI 等易挂死外设有独立恢复路径

**验证**
- [ ] 有意构造死循环，验证看门狗确实能复位
- [ ] 有意构造任务卡死，验证任务监控确实能停止喂狗
- [ ] 连续 72 小时稳定性测试，观察复位计数是否增长

最后一条最重要：**没有验证过的看门狗，等于没有看门狗。** 必须在开发阶段主动"杀死"系统，确认它能自己活过来。

## 结语

可靠性设计的本质，是**承认自己写的代码一定会出错，然后为错误准备好退路**。回到本文最核心的四点：

1. **喂狗的位置决定了看门狗是否有效**——放在中断里等于没装，放在阻塞等待里等于取消保护。唯一正确的位置是"确认系统确实完成了本轮工作之后"。
2. **IWDG 和 WWDG 解决不同问题**——IWDG 兜底防死机，WWDG 用窗口机制防"程序跑乱后喂狗过快"。严肃产品两者都要。
3. **多任务环境下必须做任务级监控**——心跳位图 + 唯一监督任务喂狗，是 FreeRTOS 项目量产的标准配置。
4. **没有诊断的复位是没有价值的**——读 `RCC_CSR`、写备份寄存器、打印故障现场，才能把"设备莫名死机"变成"task_comm 在第 4721 轮失联"。

本文的嵌入式专题已覆盖 GPIO（#01）、UART/DMA（#02）、NVIC 中断（#03）、I2C/SPI（#04）、定时器（#12）、FreeRTOS（#18）、ADC 采集（#21）与本篇的看门狗与可靠性。下一篇，我们将转向 **Qt 专题**，深入 **Qt 网络编程**：从 `QTcpSocket` 的异步 I/O 模型到 TCP 粘包拆包，再到构建一个可用的 TCP/UDP 网络调试助手——它会与 #09 的串口调试助手形成完整的上位机工具链。

---

*本文代码基于 STM32F4 HAL 库 + FreeRTOS，已在 STM32F407 上验证；监控框架部分为纯 C + CMSIS-RTOS API，可移植到其他 RTOS。*
