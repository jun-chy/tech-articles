# Qt 事件循环与事件分发机制：从 QEventLoop 到自定义事件

> 作者：蔡浩宇 | Qt/C++ 桌面开发笔记

## 引言

很多 Qt 开发者写了多年代码，对信号槽、定时器、界面刷新都"会用"，却始终没搞清一件事：**为什么 `QTimer` 不阻塞界面？为什么 `widget->show()` 之后窗口能持续响应点击？为什么在子线程里直接操作控件会崩溃？** 这三个问题的答案，都指向同一个核心——**事件循环（Event Loop）与事件分发（Event Dispatch）**。

Qt 是一个**事件驱动**的框架。理解事件循环，就理解了 Qt 的心脏：它是 GUI 能"活"起来的原因，是信号槽在跨线程时被排队投递的通道，也是 `processEvents()` 这个"看似方便实则危险"的 API 背后的原理。本文带你从 `QEventLoop` 的运转机制，一路深入到 `notify()`、事件过滤器、自定义事件与多线程。

---

## 1. 什么是事件循环

一个事件循环本质上是一个**"取事件 → 派发事件 → 再取事件"**的死循环。用伪代码表示，Qt 的主线程就是这样一个循环：

```cpp
// Qt 事件循环的核心逻辑（伪代码）
while (!exit_requested) {
    // 1. 从事件队列中取出下一个事件（可能阻塞等待）
    QEvent *event = get_next_event();

    // 2. 把事件交给目标对象处理
    QCoreApplication::notify(receiver, event);

    // 3. 处理完（或被 deleteLater 的延迟删除等）
    process_post_events();
}
```

`QCoreApplication::exec()` 启动的就是这个循环。这就是为什么下面这段代码能"永久运行"：

```cpp
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    MainWindow w;
    w.show();          // show() 投递了一个 show 事件，返回后由循环派发
    return app.exec(); // 进入事件循环，程序"活"了
}
```

**关键点**：`show()` 并不立即绘制，而是投递一个事件到队列；`exec()` 启动循环后才真正派发它。所以"事件循环"就是那个让所有 `QEvent` 得以被处理的引擎。

## 2. 事件的种类与来源

Qt 中的"事件"是一个 `QEvent` 对象，来源五花八门，但都可以统一成同一套分发机制：

| 来源 | 例子 | 事件类型 |
|------|------|---------|
| 系统/窗口 | 鼠标、键盘、重绘、关闭 | `QMouseEvent`、`QKeyEvent`、`QPaintEvent` |
| 定时器 | `QTimer` 到期 | `QTimerEvent` |
| 网络/IO | Socket 可读、文件就绪 | `QSocketNotifier` 触发的 `QEvent` |
| Qt 内部 | 信号槽跨线程排队、`deleteLater` | `QMetaCallEvent`、`QDeferredDeleteEvent` |
| 用户自定义 | 自定义事件 | `QEvent::User` 及更高 |

所有事件都有一个 `type()`（`QEvent::Type`）和一个 `receiver`（目标对象）。事件循环要做的，就是把这个事件**送到正确的 receiver 手里**。

## 3. 事件分发：notify() 的三级流水线

当一个事件从队列中被取出，它要经过一条**三级分发流水线**，最终落到某个 `QObject` 的具体事件处理函数上：

```
QCoreApplication::notify(receiver, event)
        │
        ▼
① 事件过滤器（Application 级）        ← installEventFilter 在 qApp 上
        │
        ▼
② 事件过滤器（对象级）                ← installEventFilter 在 receiver 上
        │
        ▼
③ receiver->event(event)             ← QObject 的事件分发入口
        │
        ▼
   具体 handler：mousePressEvent() / timerEvent() / customEvent() ...
```

### 3.1 覆写 event()：全局拦截

`QObject::event()` 是每个对象处理事件的**总入口**。覆写它，你可以在对象级别统一拦截、记录或改写事件：

```cpp
class MyWidget : public QWidget
{
protected:
    bool event(QEvent *e) override
    {
        // 拦截所有按键，F1 时不显示帮助而是自定义动作
        if (e->type() == QEvent::KeyPress) {
            auto *ke = static_cast<QKeyEvent *>(e);
            if (ke->key() == Qt::Key_F1) {
                showAboutDialog();
                return true;   // 返回 true：事件已处理，不再向下传递
            }
        }
        // 其它事件交给基类默认处理
        return QWidget::event(e);
    }
};
```

**返回值语义**：`event()` 返回 `true` 表示"事件已被我处理，停止传播"；返回 `false` 表示"没处理，继续"。这一点和信号槽完全不同——信号槽没有"返回值阻止传播"的概念。

### 3.2 notify() 覆写：全局兜底

`QCoreApplication::notify()` 是所有事件的**第一个入口**。覆写它能做全局日志、崩溃前捕获、性能埋点：

```cpp
class MyApplication : public QApplication
{
protected:
    bool notify(QObject *receiver, QEvent *e) override
    {
        try {
            return QApplication::notify(receiver, e);
        } catch (std::exception &ex) {
            // 全局异常兜底：记录后继续，避免整个程序崩溃
            qCritical() << "Exception in event handler:"
                        << ex.what()
                        << "receiver:" << receiver->objectName()
                        << "event:" << e->type();
            return false;
        }
    }
};
```

在 `main()` 里用 `MyApplication` 替换 `QApplication` 即可。这是构建**健壮桌面应用**的常用手法。

## 4. 事件 vs 信号槽：本质区别

这是最容易混淆的一对概念。它们都"能触发某段代码执行"，但机制截然不同：

| 维度 | 事件（Event） | 信号槽（Signal/Slot） |
|------|--------------|---------------------|
| 机制 | 同步派发，走 `notify() → event()` | 通过元对象系统查找连接，直接/排队调用 |
| 返回值 | 有（`bool`，可阻止传播） | 无 |
| 目标 | **单一 receiver**，明确指定 | **一对多**，可连多个槽 |
| 传播 | 有传播/拦截语义（过滤器、event 返回值） | 无传播语义 |
| 跨线程 | 事件循环是跨线程投递的**底层通道** | 跨线程时通过 `QMetaCallEvent` 走事件循环 |

**关键联系**：当你用 `connect(sender, SIGNAL(...), receiver, SLOT(...), Qt::QueuedConnection)` 做跨线程信号槽时，Qt 实际做的事是——**把这次调用包装成一个 `QMetaCallEvent`，投递到 receiver 线程的事件队列里**。也就是说，**排队连接的信号槽，底层就是事件**。等 receiver 线程的事件循环转到这个事件，才真正调用槽函数。

```cpp
// 跨线程信号槽的本质（简化）
connect(sensorThread, &Sensor::dataReady,
        ui, &UI::onDataReady,
        Qt::QueuedConnection);   // 实际：Sensor 线程投递一个 QMetaCallEvent 到 UI 线程
```

理解了这层关系，你就明白了为什么跨线程信号槽是**异步**的、为什么槽一定在 receiver 所在线程执行。

## 5. 事件过滤器：无需继承的拦截器

事件过滤器（Event Filter）让你在**不继承目标类**的情况下拦截它的事件——这是 Qt 最优雅的机制之一：

```cpp
// 让一个普通对象监视另一个对象的事件
class KeyMonitor : public QObject
{
    bool eventFilter(QObject *watched, QEvent *event) override
    {
        if (event->type() == QEvent::KeyPress) {
            auto *ke = static_cast<QKeyEvent *>(event);
            qDebug() << "Key" << ke->key() << "on" << watched->objectName();
        }
        return QObject::eventFilter(watched, event);  // 继续传播
    }
};

// 安装：monitor 开始监视 lineEdit 的所有事件
KeyMonitor *monitor = new KeyMonitor(lineEdit);
lineEdit->installEventFilter(monitor);
```

经典应用场景：

| 场景 | 做法 |
|------|------|
| 输入框只允许数字 | 过滤器里拦截非法字符，返回 `true` 吃掉 |
| 全屏按钮拦截回车 | 过滤 `KeyPress` 中的 `Enter` |
| 无侵入式埋点 | 对 `qApp` 安装过滤器，统计所有点击 |
| 让 QLabel 可点击 | 过滤 `MouseButtonPress` 转发成自定义信号 |

**注意**：过滤器里返回 `true` 会**阻止事件继续向下传递**，目标对象就收不到这个事件了。这是"吃掉"事件的正确姿势。

## 6. 自定义事件与 sendEvent/postEvent

当标准事件不够用，你可以定义自己的事件类型，在对象之间传递。

### 6.1 注册事件类型

```cpp
// 全局注册一次，拿到唯一的事件类型 ID
const QEvent::Type MyCustomEventType =
    static_cast<QEvent::Type>(QEvent::registerEventType());

class MyCustomEvent : public QEvent
{
public:
    MyCustomEvent(int payload)
        : QEvent(MyCustomEventType), m_payload(payload) {}
    int payload() const { return m_payload; }
private:
    int m_payload;
};
```

### 6.2 发送 vs 投递

这是理解 Qt 事件模型**最核心的一对区别**：

```cpp
// ① sendEvent：同步，立即在当前线程调用 receiver 的事件处理
QApplication::sendEvent(receiver, new MyCustomEvent(42));
//    → 等价于直接调用 notify()，receiver 的事件处理函数在当前线程同步执行完毕

// ② postEvent：异步，把事件加入 receiver 线程的事件队列，稍后由事件循环派发
QApplication::postEvent(receiver, new MyCustomEvent(42));
//    → 立即返回，事件在 receiver 线程的事件循环里被处理
```

| 维度 | `sendEvent` | `postEvent` |
|------|-------------|-------------|
| 执行时机 | **同步立即** | **异步排队** |
| 执行线程 | 调用者线程 | receiver 所属线程 |
| 返回时机 | 事件处理完才返回 | 入队后立即返回 |
| 内存 | 事件对象需调用者管理 | 事件对象由 Qt 在派发后自动 delete |
| 用途 | 需要立即结果、同线程通信 | **跨线程通信、解耦、延迟处理** |

**工程规则**：跨线程通信**必须用 `postEvent`（或排队信号槽）**，因为 `sendEvent` 会同步执行 receiver 线程里的事件处理函数，绕过 receiver 的事件循环，破坏其线程安全。这一点和"不能在子线程直接操作控件"是同一道理。

### 6.3 接收自定义事件

```cpp
class Worker : public QObject
{
protected:
    void customEvent(QEvent *event) override
    {
        if (event->type() == MyCustomEventType) {
            auto *e = static_cast<MyCustomEvent *>(event);
            qDebug() << "收到自定义事件，payload =" << e->payload();
        }
    }
};
```

## 7. 事件循环与多线程

Qt 最常被误解的一点：**每个线程都可以有（也可以没有）自己的事件循环**。

```cpp
class WorkerThread : public QThread
{
    void run() override
    {
        // 关键：启动本线程自己的事件循环
        exec();   // 让该线程能处理投递给它的 postEvent / 排队信号槽
    }
};
```

规则总结：

```
主线程：QApplication::exec() 天然拥有事件循环
子线程：默认 QThread::run() 只是执行一段代码，没有事件循环！
       → 需要调用 exec() 才能处理事件
       → 或用 QThread::eventDispatcher 建立
```

**这就是"子线程不能直接操作控件"的根本原因**：控件属于主线程，其事件处理函数必须在主线程执行。子线程若直接调用 `label->setText()`，等于跨线程执行 GUI 操作，会触发 Qt 的断言或未定义行为。正确做法是把操作投递回主线程：

```cpp
// 子线程里安全地更新 UI
QMetaObject::invokeMethod(label, "setText",
                          Qt::QueuedConnection,
                          Q_ARG(QString, "更新了"));
// 或 emit 一个信号，用排队连接连到主线程的槽
```

## 8. 定时器：事件循环里的一等公民

`QTimer` 不是独立线程，它**寄生在事件循环里**。定时器到期时，事件循环产生一个 `QTimerEvent` 派发给目标对象：

```cpp
// 方式1：信号槽（最常用）
QTimer *timer = new QTimer(this);
connect(timer, &QTimer::timeout, this, &MainWindow::onTimeout);
timer->start(1000);   // 每 1 秒触发一次

// 方式2：覆写 timerEvent（更底层）
class Widget : public QWidget {
protected:
    void timerEvent(QTimerEvent *e) override {
        if (e->timerId() == m_timerId) { /* ... */ }
    }
private:
    int m_timerId = startTimer(1000);
};
```

**重要结论**：因为定时器依赖事件循环，如果主线程被一段长循环阻塞（比如 `while` 里做大量计算），**定时器会"卡住"不触发，界面也会冻结**。这正是下面要讲的 `processEvents()` 陷阱。

## 9. processEvents()：看似方便，实则危险

当主线程要做耗时操作、又不想界面冻结时，很多人会这样写：

```cpp
// ❌ 反模式：在耗时循环里手动泵事件
for (int i = 0; i < 1000000; ++i) {
    do_heavy_computation(i);
    QCoreApplication::processEvents();   // 让界面喘口气
}
```

这样确实能让界面不卡死，但埋下了**重入（reentrancy）**的定时炸弹：

```
风险链条：
processEvents() 派发了一个按钮点击事件
  → 用户点击了"取消"按钮，触发了某个槽
    → 该槽删除了正在循环里使用的对象
      → 回到循环，继续访问已删除的对象 → 崩溃
```

**正确做法**是把耗时操作移到子线程，或用 `QtConcurrent`，让主线程事件循环保持干净：

```cpp
// ✅ 正确：耗时计算放子线程
auto *watcher = new QFutureWatcher<void>(this);
connect(watcher, &QFutureWatcher<void>::finished, this, [=] {
    ui->progressBar->setValue(100);
});
QFuture<void> future = QtConcurrent::run([=] {
    for (int i = 0; i < 1000000; ++i)
        do_heavy_computation(i);
});
watcher->setFuture(future);
```

**结论**：`processEvents()` 可以用于短平快的"让界面刷新一下"（如显示进度后立即重绘），但**绝不要用它来支撑长耗时逻辑**。遇到耗时操作，第一时间想"能不能放到子线程"。

## 10. 调试与常见陷阱清单

| 症状 | 根因 | 解决 |
|------|------|------|
| 界面卡死/无响应 | 主线程被长循环阻塞，事件循环停止运转 | 耗时操作移子线程 |
| 定时器不触发 | 同上，事件循环被阻塞 | 同上 |
| 子线程操作控件崩溃 | 跨线程 GUI 操作 | 用 `invokeMethod(QueuedConnection)` 或信号槽 |
| 点击按钮无反应但程序没死 | 事件被过滤器/`event()` 返回 `true` 吃掉 | 检查过滤器返回值 |
| 崩溃但异常无处捕获 | 事件处理函数抛异常，未兜底 | 覆写 `notify()` 做全局 try-catch |
| `deleteLater` 没生效 | 对象线程无事件循环 | 子线程里调用 `exec()` |

## 结语

事件循环是 Qt 的"心脏"，事件分发是它的"血管"。搞懂了 `QEventLoop` 如何取事件、`notify()` 如何把事件送到正确的 receiver、事件与信号槽在跨线程时如何合流，你就拥有了解释 Qt 一切"奇怪行为"的钥匙：为什么界面会卡、为什么定时器不触发、为什么子线程不能碰控件、为什么 `processEvents()` 会埋雷。
